# Architecture Deep Dive: ARM64 vs. x86_64 Boot Chains

When adapting a minimal Linux system between ARM64 and x86_64, several fundamental architectural differences arise. Understanding these differences demystifies how the Linux kernel initializes different processor hardware.

---

## 1. Summary Comparison

| Mechanism | ARM64 (`aarch64`) | x86_64 (`amd64`) |
| :--- | :--- | :--- |
| **Kernel Binary Format** | Flat uncompressed binary (`Image`) or `Image.gz` | Self-decompressing hybrid (`bzImage`) |
| **Firmware Entry State** | 64-bit Exception Level 1 (EL1) or EL2 | 16-bit Real Mode (legacy) or 32-bit Protected Mode / 64-bit via EFI |
| **Boot Parameter Handover** | Flattened Device Tree (`dtb`) in register `x0` | Zero-Page (`boot_params`) struct setup by bootloader |
| **Hardware Discovery** | Device Tree (FDT) or ACPI | ACPI (Modern) + PCI bus discovery + legacy PC I/O ports |
| **Primary Serial Port** | ARM PrimeCell PL011 MMIO (`ttyAMA0`) | National Semiconductor 8250/16550 UART (`ttyS0`) |
| **QEMU Machine** | `virt` (generic virtualized ARM platform) | `q35` (modern PCIe/ICH9) or `pc` (legacy i440FX) |
| **Hypervisor Acceleration** | Apple Silicon: `hvf`, Linux ARM: `kvm` | Windows: `whpx`, Linux: `kvm`, macOS: `hvf` |

## 2. Kernel Binary Structure: `Image` vs. `bzImage`

### ARM64 `Image`
The ARM64 kernel output `arch/arm64/boot/Image` is a raw binary:
- **Header:** 64-byte header starting with a branch instruction and magic bytes `ARM\x64` (`0x644d5241`).
- **Decompression:** ARM64 kernels do not typically decompress themselves; decompression is delegated to firmware (UEFI) or the bootloader (U-Boot, GRUB).
- **Execution:** Execution begins directly in 64-bit mode at the specified text offset.

### x86_64 `bzImage` ("Big zImage")
The x86_64 kernel binary `arch/x86/boot/bzImage` is a complex composite structure:
- **Real-mode Setup Code:** Contains legacy 16-bit x86 code required for booting from MS-DOS/legacy BIOS.
- **Decompression Stub:** Contains 32-bit protected mode code that decompresses the payload (`vmlinux.bin`) using gzip, xz, or zstd.
- **Long Mode Switch:** After decompression, the startup code sets up page tables, enables PAE, sets the `EFER.LME` bit, enables paging in `CR0`, and jumps into 64-bit Long Mode (`startup_64`).

## 3. Serial Console: Why `ttyAMA0` vs. `ttyS0` Matters

A common source of confusion when transitioning architectures is the kernel boot parameter `console=`:

### On ARM64 QEMU (`virt` board):
- The serial device simulated by QEMU is the **ARM PrimeCell PL011 UART**.
- The Linux driver for this hardware registers devices under `/dev/ttyAMA0`, `/dev/ttyAMA1`, etc.
- Passing `console=ttyS0` sends output to a non-existent device, resulting in complete silence (black screen).

### On x86_64 QEMU (`q35` or `pc` board):
- The serial device is modeled after the classic IBM PC **8250/16550 UART**.
- It communicates via x86 I/O port `0x3F8` and IRQ 4.
- The standard Linux 8250 serial driver binds this to `/dev/ttyS0`.
- Passing `console=ttyAMA0` on x86_64 will fail because the driver does not exist for PC architecture.

## 4. Hardware Description: Device Tree vs. ACPI

### ARM64 (Device Tree)
ARM architectures have historically lacked a standard PC-style hardware discovery mechanism (like PCI configuration space). Therefore, firmware passes a compiled Device Tree (`.dtb`) to the kernel in memory. The kernel reads this tree to discover:
- Memory banks and RAM sizes
- Interrupt controller addresses (GIC)
- Timer frequencies
- MMIO peripheral base addresses

### x86_64 (ACPI & Legacy PC)
x86 architectures standardize motherboard components:
- Fixed I/O port assignments (e.g., PIC at `0x20`, PIT at `0x40`, Serial at `0x3F8`).
- ACPI tables (RSDP, FADT, MADT, DSDT) provided by the BIOS/UEFI.
- PCI/PCIe bus scanning where devices advertise Vendor and Device IDs in configuration space.
